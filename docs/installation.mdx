## Install

```bash
npm install mujoco-react @react-three/fiber @react-three/drei three
```

### Peer Dependencies

| Package | Version | Purpose |
|---------|---------|---------|
| `@react-three/fiber` | `>=8` | React renderer for Three.js |
| `@react-three/drei` | `>=9` | R3F helpers (PivotControls, etc.) |
| `three` | `>=0.180` | 3D rendering |
| `react` | `>=18` | React |

`@mujoco/mujoco` is installed by `mujoco-react` as the underlying MuJoCo WASM engine. The engine is pinned to an exact version so dependency updates cannot silently change simulation behavior.

### Engine versions

mujoco-react installs MuJoCo 4.0.1. Contact and settling behavior can differ between MuJoCo releases, so an app can run the exact release its reference data came from by overriding the engine in its `package.json`. npm and bun:

```json
{
  "overrides": { "@mujoco/mujoco": "3.11.0" }
}
```

pnpm:

```json
{
  "pnpm": { "overrides": { "@mujoco/mujoco": "3.11.0" } }
}
```

Yarn:

```json
{
  "resolutions": { "@mujoco/mujoco": "3.11.0" }
}
```

Use an exact version, and reinstall after changing it. If your app also depends on `@mujoco/mujoco` directly, pin that dependency to the same version so the app and mujoco-react share one engine.

mujoco-react supports every release from 3.8.1 through 4.0.1 and runs its engine test suite against each one (`npm run test:engines`). On 3.x engines:

- Models loaded by mujoco-react get the MuJoCo 4 field shapes the library reads: `actuator_ctrlnum`, `actuator_ctrladr` and `nactuator` before 3.11 (one control per actuator), `Int32Array` `tex_adr` before 3.14, and the boolean model arrays (`jnt_limited`, `light_active`, `light_castshadow`, `mat_texuniform`, `tendon_limited`, `eq_active0`, and others) that the 3.9–3.14 bindings cannot read. These are read-only copies. Recovering the boolean arrays prints the model once per load, which adds about 0.2 s for a LIBERO scene.
- MuJoCo 4 features are unavailable: speculative contacts, yielding springs, and `data.plastic`.
- `threadCount` requires 3.10 or later.
- Loading many different scenes in one page can exhaust the engine's WASM memory. 3.x engines ran out after about 24 distinct LIBERO scenes; 4.0.1 loaded all 130. Reloading the same scene does not grow memory. A page reload starts a fresh engine.

### Upgrading to MuJoCo 4

When upgrading from the previous engine, review the [upstream migration notes](https://github.com/google-deepmind/mujoco/releases/tag/4.0.0). Existing models can behave differently: tendon wrapping, ball/free-joint RK4 integration, and flex elasticity have changed. Cable plugins and composite elements must migrate to flexcomp; flex edge stiffness/damping cannot be used with the discrete integrator. Recheck model trajectories and regenerate snapshots after upgrading.

The React interface and default single-threaded WASM setup are unchanged. Threaded WASM remains opt-in.

### TypeScript

```bash
npm install -D @types/three
```

mujoco-react ships with full TypeScript types. No `@types/` package needed for the library itself.

## Bundler Setup

### Vite (Recommended)

`@mujoco/mujoco` ships a `.wasm` asset. Vite serves package WASM assets correctly with the standard React setup:

```ts
// vite.config.ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
});
```

### Next.js

Since MuJoCo uses WASM and browser APIs, it must run client-side only:

```tsx
import dynamic from "next/dynamic";

const MujocoApp = dynamic(() => import("./MujocoApp"), { ssr: false });
```

### Create React App

Works out of the box. No additional configuration needed.

### Multi-Threaded WASM

`MujocoProvider` defaults to the single-threaded official MuJoCo WASM build. To opt into the official multi-threaded build:

```tsx
import loadMujocoMt from "@mujoco/mujoco/mt";
import mtWasmUrl from "@mujoco/mujoco/mt/mujoco.wasm?url";

<MujocoProvider
  wasmVariant="auto"
  threadedLoader={loadMujocoMt}
  threadCount={2}
  mtWasmUrl={mtWasmUrl}
>
  <App />
</MujocoProvider>
```

`"auto"` only loads the threaded build when `threadedLoader` and `mtWasmUrl` are provided and the browser reports `globalThis.crossOriginIsolated === true`. If you force `wasmVariant="threaded"`, your dev server and production host must send:

```txt
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

## Verify Installation

```tsx
import { MujocoProvider, MujocoCanvas } from "mujoco-react";

function App() {
  return (
    <MujocoProvider>
      <MujocoCanvas
        config={{
          src: "https://raw.githubusercontent.com/google-deepmind/mujoco_menagerie/main/franka_emika_panda/",
          sceneFile: "scene.xml",
        }}
        style={{ width: "100%", height: "100vh" }}
        onReady={({ api }) => {
          console.log("MuJoCo loaded!", api.getBodies().map(({ name }) => name));
        }}
        onError={(err) => console.error("Load failed:", err)}
      >
        <ambientLight />
      </MujocoCanvas>
    </MujocoProvider>
  );
}
```

If you see a Franka Panda robot in your browser, everything is working.

<Note>
  The first load may take a few seconds as the WASM module initializes and model assets are fetched from GitHub. Subsequent loads are faster due to browser caching.
</Note>

`threadCount` defaults to 0. Set a positive integer to initialize `mju_threadpool`
for each simulation data instance. It requires the threaded build and cross-origin
isolation. Loading the MT build alone does not request a simulation thread pool.
Benchmark your scene before increasing the count; small scenes can be slower.

## Worker runtime in Vite

The `mujocoReact` plugin preserves worker asset URLs by excluding `mujoco-react` from dependency prebundling. If you omit the plugin, add `optimizeDeps: { exclude: ["mujoco-react"] }` to Vite config before using `api.createRuntime()`. See [worker simulation](/guides/simulation-runtime).
